## 0. 铁律（违反其一即为缺陷）

| # | 铁律 | 落地方式 |
|---|---|---|
| 1 | 比率一律 **0~1** 存储 | 后端一律 `ratio = a / b`；百分号只在 Client 渲染层加 |
| 2 | 取不到 = `null`，绝不 = `0` | 0 意味着「真的为零」，是误导 |
| 3 | 完成率**自己算** | `完成率 = 区间签约额 ÷ 年度军令状目标`；**禁用**上游 `signing_completion_rate`（分子区间、分母年度） |
| 4 | 两套业绩字段**不可混用** | `total_performance_analysis.order_total_amount` ≠ `sales_performance_ranking.signing_amount`；一个模块内只用一套，并在「口径与数据」页注明用的是哪套 |
| 5 | STD 判定必须 **code 精确相等** | `std_product_info_query` 的 code 过滤是 LIKE 前缀匹配，会多返回 `RM758338MD6` 这类更长货号 |
| 6 | 穷尽读取要**如实登记 completeness** | `read/total/totalKnown/complete/missing/reason`，宁可承认不完整 |
| 7 | 部分源失败**降级不 reject** | 单源失败 → 该指标 `null` + `warnings` + `calls[].note`；整体仍返回 200 |
| 8 | 缓存以**有没有取数失败**为准 | `calls[].ok===false` 为 0 条即入缓存；告警是口径提示，随结果一起缓存（否则恒有 1 条 STD 预算告警 → 缓存永不命中 → 每次重拉 3~5 分钟） |
| 9 | PII 不落盘 | 电话/地址/身份证/银行账号不写文件、不进缓存、不出接口响应 |
| 10 | 抽样池必须**按成交额排序** | 用 `total_performance_analysis.top_customers`；`customer_analysis.data.sales[]` 带区间只回 36 行，覆盖率仅 1.9% |
| 11 | 分母必须说清是谁 | 复购只算 `orderCount ≥ 1`（其余进 `excludedNoOrder`）；沉睡给 `sampleSize`/`sampleTotal` |
| 12 | 慢上游必须**串行 + 放宽超时** | std 服务单 session 串行、单条 6~8 秒 → 并发探测会全部超时（STD 占比变 null）；逐个 await + 单次 60s + 墙钟封顶 |
| 13 | 人员类指标**先判序列再入表** | `staff_info` 是全公司花名册；新兵 = **尚未转正**的业务咨询成员（`positive_time` 为空、或晚于基准日），先判销售序列（`first_dep_name=业务咨询事业群`，或 `dep_name`/`second_dep_name` 命中销售二级部门白名单），再剔除 `status===0`（离职）、非销售岗（`post_name` 不是「业务咨询经理」）与已转正；`status_name` 是乱码，只能用数值；**不可用「job_no 以 YX 开头」当判据**（市场部业务员10也是 YX90017，实测会漏进非销售） |
| 14 | AI 对话只发 **user 角色**历史 | assistant 带正文会让 DSH llm 服务抛 `Cannot read properties of undefined (reading 'replayState')` → 全候选模型失败 → 接口 500 |
| 15 | 阈值必须**可配置且可见** | 阈值只走 `resolveThresholds(settings.thresholds)`，非法值回退默认；生效值随 `meta.thresholds` 下发并在页面第 10 页签展示，不散落在业务逻辑里 |
| 16 | 上游脏数据**归并要留痕** | 梯队名坏字节（`"<U+FFFD×3>狼特战队"`）按最长公共后缀归并，**唯一命中且后缀 ≥3 字**才并，否则保留原名；每次归并写一条 `warnings`，绝不悄悄改数 |
| 17 | PII 扫描**必须排除小数点** | 前后视断言写成 `(?<![0-9.]) … (?![0-9.])`；只排除数字时浮点数会被误判成身份证/座机 → 磁盘缓存永远写不进去 + 每次显示不实的「含敏感信息」告警 |
| 18 | MCP 工具名前缀**不得写死** | 工具全名 = `mcp__<连接器名>__<工具名>`，连接器名每台设备自己起。启动时读 `<DSH_HOME>/storages/mcp_connector.json`（只读 `serverName`/`url`/`enabled`，**绝不读 `auth.apiKeyValue`**）按端口认领（8001=erp / 8006=std / 8003=planning），再按名，最后回退默认；优先级 = 配置 > 端口 > 名称 > 默认。首选不可见才试兜底前缀，**真实错误立即停**；生效值随 `meta.toolPrefixes` / `meta.toolPrefixSource` 下发并在页签 10 展示 |
| 19 | **未回款额必须归一** | `uncollectedAmount = 签约 − 已回款`；上游 `uncollected_amount` 把**部分回款按全额计入**，虚高；原值另存 `uncollectedAmountUpstream`，差额进 `notes` |
| 20 | **逾期天数必须归一** | 上游给的是「距账期到期日的天数」，**负数 = 还没到期**；负数置 `null` + 布尔 `overdue`（>0 才 true）；取不到时 `overdue=null` |
| 21 | **四套口径互不混用** | `periodMetrics`=区间；`lifetime`=客户全周期；`rating.metrics`=近 12 个月；`benchmark`=总盘。卡片分别标注，不跨口径比较 |
| 22 | **同名多主体不猜** | 客户名命中多主体 → `resolved.candidates` + `ambiguous=true`，由用户点选；不默认选第一个、不加总 |
| 23 | **省份绝不靠公司名猜** | 优先级 = `country===1`（海外）→ 信用代码第 3-4 位省码 → 地址省名前缀 → 地址地级市表 → `area_name`；都不中落 `uncovered` 并在页面列出；地图**只放内存缓存不落盘** |
| 24 | **PII 红线（实体档案加严）** | 电话/座机/邮箱/地址/统一社会信用代码/银行账号/法人/官网/备注一律不进 payload 与缓存；`visits[]` 只留白名单字段（上游 `visits[].data` 里的收件人电话、地址必须剥掉）；`customer_info` 的明文地址只用于**当场解析省份**，不外发 |
| 25 | **实体档案必须限流** | `detailBudget` / `geoBudgetMs` / `geoMaxRequests` 三重封顶；超预算即停手并在 `warnings` + `completeness` 写明「取到多少、还差多少、为什么停」 |
| 26 | **报价 TOP 榜双口径** | `share`=样本内占比；`shareOfTotal`=÷ 全量报价额（与 KPI 同分母）；块级给 `basis:'sample'`+`sampleAmount`+`sampleShare`；页面必须写「TOP10 基于 N 份抽样，不是全量 TOP10」 |
| 27 | **上游 limit 硬钳 500** | 传多大 limit 都只回 500 行；同响应的 `overview.order_count` 才是真实单数 → 截断判定用 `orders.length < overview.order_count`，需全量时按日期对半拆窗（深度 ≤2）+ `sale_id`/`sale_code` 去重 |
| 28 | **订单状态码不猜但可标注推断** | `saleState` 保留 ERP 原始码；`saleStateLabel`（1=在途未完成、2=已完成）是**实测推断非官方码表** —— 依据 2026-01/04/08：码 1 的 45 单回款率 17.8%、码 2 的 260 单回款率 92.3%。前端优先显示 label，缺失退「状态码 N」，notes 注明推断 |
| 29 | **回款率不自相矛盾** | `collection.overview.collectionRate` 由 `collection_amount ÷ signing_amount` 自算（signing=0 或取不到 → `null`），与 `periodMetrics.collectionRate` 同源同分母 |
| 30 | **配色只取 DSH 设计系统别名** | v1.2.0 起全部颜色走 `var(--令牌, #兜底)`，令牌在 `.esd-root`/`.esdc-root`/`.esd-shell` 三个根同时声明；色板与 ERP 业务工作台一致（`label-primary/secondary/tertiary` + `brand-primary` + `state-*`），详见 `docs/配色规范.md` |
| 31 | **CSS 结构必须体检** | 括号配平 + 关键规则进 CSSOM；顶层游离 `}` 会让 Chromium 整条丢弃紧随其后的规则（曾致 `.esd-root` 根规则失效、文字退回宿主黑） |

## 0·五、配色口径（v1.2.0）

配色本身不产生数据，但它决定**数字能不能被读懂**——所以和口径一样受铁律约束：

- **与 ERP 业务工作台同色板**：主文字 `label-primary`（`#f9fafb`）、次文字 `label-secondary`（`#cfd3d6`）、
  弱化 `label-tertiary`（`#adb2b8`）、强调 `brand-primary`（`#f9fafb`）、
  状态色 `state-error/warn/success/idle-primary`（`#f25a5a`/`#f59e0b`/`#22c55e`/`#545557`）、
  底色 `bg-base`/`bg-layer-1`/`bg-layer-2`（`#151517`/`#232324`/`#2c2c2e`）。
- **状态语义靠颜色区分**：达标=绿、预警=橙、超限=红、无数据=中性灰；状态文字用**原始状态色**，
  不用浅色变体（浅色变体在小字号下对比度不足，容易被读成普通文字）。
- **颜色不承载数据**：同一含义在全插件只有一种颜色（达标永远绿），不做「红黄绿三色主题」这类按数据重映射。
- **地图色阶是「相对密度」而非「好坏」**：`--esd-geo-lv0..lv5` 按客户数分 6 档，
  客户多 = 深、覆盖度差异不代表优劣，不得解读成风险色。
- 完整映射、语义规则与验收方法见 **`docs/配色规范.md`**。

## 1. 业绩口径（方案 02）

### 1.1 双口径业绩总额（思路文档明确要求）

| 指标 | 定义 | 公式 | 源 |
|---|---|---|---|
| **签单额（区间）** | 区间内新签订单金额 | 直接取 | `total_performance_analysis.overview.order_total_amount` |
| **完成额（区间）** | 区间内完成（含税确认）金额 | 直接取 | `overview.finish_amount`（或 `acceptance_amount`） |
| **年度累计签单额** | 本年 1/1 → 今日 | 同上，取年度区间 | 同上 |
| **当年签单当年完成额** | 本年签单的订单里，本年完成的部分 | 取年度区间的 finish 字段 | 同上 |
| **目标完成率** | 业绩目标完成率 | `区间签约额 ÷ 年度军令状目标` | `sales_performance_ranking.target_amount`（**成员级**）+ 目标汇总 |
| **业绩完成率** | 当年签单当年完成 | `当年签单当年完成额 ÷ 当年签单额` | 自算 |
| **同比** | 与去年同期比 | `(本期 − 去年同期) ÷ 去年同期` | 去年同期同口径再跑一次 |
| **环比** | 与上月比 | `(本期 − 上月) ÷ 上月` | `overview.trend[]` 相邻月 |

> **注意**：上游 `signing_completion_rate`（如 114.71）= 区间签约额 ÷ **年度**目标。
> 当区间是"本月"时，它天然小于真完成率，但**分子分母不同期**，不能叫"完成率"。
> 本插件一律自算并标注区间。

### 1.2 预警阈值（思路文档）

| 条件 | 状态 |
|---|---|
| 同比/环比降幅 > 20% | 红（bad） |
| 降幅 20% ~ 0 | 黄（warn） |
| 增长或持平 | 绿（good） |

**v6 起阈值全部可配置，唯一真相源是 `cordis.patch.yml` 的 `config.thresholds`**：

```yaml
- id: erp-sales-dashboard
  name: "@local/erp-sales-dashboard"
  config:
    thresholds:
      stdShare: 0.6        # STD 营收占比目标
      bShare: 0.4          # B 类订单占比目标
      cShare: 0.15         # C 类订单占比上限
      collectionRate: 0.9  # 回款率目标
      growthDrop: 0.2      # 同比/环比降幅红线
```

- Host 半统一走 `resolveThresholds(settings.thresholds)`：只写要改的键即可，其余保持默认；
  **非法值（NaN / 越界 0~1 / 负数）自动回退默认**，不静默变成 0。
- 派生黄线（占位目标上下的 ±20% 带宽）按「目标 × 0.8」自动重算，不需要另外配。
- 实际生效值随 `meta.thresholds` 下发，页面第 10 页签有「智能预警阈值（本次生效）」卡片，
  **不靠文字说明**，让「红黄绿阈值是谁定的、改了没有」可见可查。
- 阈值不散落在业务逻辑里：所有 good/warn/bad 判定都读同一份 resolved 结果。

### 1.3 梯队名称归并（上游坏字节）

**现象**：`sales_performance_ranking` 里 0 业绩的占位成员「占位成员01」，
其 `department_name` 在 MCP 侧被解成 `"<U+FFFD×3>狼特战队"`（库里「战狼特战队」的「战」字是坏字节）。
它会在 top-N 截断时被切进来，页面上就多出一条「0 人的假梯队」。

**归并规则**（`metrics.normalizeSquadName`）：

1. 剥掉所有 Unicode 替换字符（`\uFFFD`）与不可见字符，得到可读尾巴；
2. 与已知梯队名列表（鲲鹏特战队 / 猛虎特训营 / 海豹特战队 / 战狼特战队 / 蛟龙特训营 / 业务咨询事业群）
   求**最长公共后缀**；
3. **唯一命中且公共后缀长度 ≥ 3** 才归并到该梯队；否则**不猜**，保留原名并告警；
4. 归并结果记入 `squadMergeLog`，并**至少写一条 `warnings`**，页面第 10 页签可见。

**顺序要求**：归并必须发生在**梯队筛选之前**。否则按「战狼特战队」筛选时，
被归并的成员会因为原名不匹配而被漏掉。

> **根因在上游**：坏字节在 ERP 库里，插件只能识别与归并，**彻底修复需要运维侧改数据**。
> 插件的做法是「识别 + 归并 + 留痕」，不猜、不静默、不假装数据是干净的。

## 2. 订单质量（方案 02 (3/4)）

### 2.1 A/B/C 加权业绩模型

思路文档给出：**业绩总额 = 1×A + 1.2×B + 0.5×C**，并要求"系数可自行调整"。

- 实现：系数放在 config（`abcWeights: { a: 1, b: 1.2, c: 0.5 }`），UI 可临时改，默认即文档值。
- 展示：加权值与原始签单额**并列**，并给出 2025/2024 同期按同系数重算的对比值。
- **数据现实**：`yx_sale.sale_level`（2 = B 类）**不在** `sales_order_collection_analysis` 的返回里，
  只有 `customer_tier_rating.metrics.b_order_share` 间接给出某客户的 B 类占比，
  且该接口**每次只能查一个客户**（实测：不带客户标识直接报"请至少提供 customer_name、customer_code 或 customer_pk 之一"）。
  → 团队级 ABC 只能**抽样**（`tierSampleSize`），页面必须显示：样本客户数 / 抽样方式 / 覆盖率。
  - 抽样池见 §4.1：必须用 `total_performance_analysis.top_customers`（按区间成交额降序），
    用 `customer_analysis.data.sales[]` 只能覆盖 1.9%。

### 2.2 STD 品牌占比（v1.4.0 起改为**签单金额口径**）

> 旧口径（v1.3.0 及以前）是**报价单金额**，用户 2026-11-04 明确要求改成**签单金额**：
> 报价只是意向，签单才是收入。旧实现保留在 payload 的 `quoteAmount` / `stdAmount` 字段里作对照。

**口径链条**（三个上游接口串起来，缺一不可）：

1. `product_efficiency_analysis(metric='inventory_shipping', start_date, end_date, limit)`
   的 `data.details[]` 给出 **订单 → 货号** 的对应关系
   （每行含 `sale_code / goods_code / goods_name / goods_batch / out_code / start_time / end_time`）。
   - ERP 的销售订单行**本身不带货号**，这是唯一能拿到「某张订单卖了哪些货号」的接口。
   - `details` 被上游 limit **硬顶 500 行**（实测 2026-10 一个月 739 行）→ `summary.total_count > 取到的行数`
     即判截断，按日期对半拆窗口重取（`SHIP_MAX_DEPTH = 2`）。
2. `sales_order_collection_analysis.orders[]` 给 `sale_code → signing_amount`（同区间）。
   - 同样硬顶 500 行，判截断用同响应的 `overview.order_count`，按日期对半拆。
3. 订单签单额 **按该订单的货号行数平均分摊**到每一行。
   - ⚠️ 这是**近似**：单货号订单精确，多货号订单按行均摊（实测 2026-10 多行订单 96 张、平均 1.89 行）。

**STD 判定**：逐货号查 `std_product_info_query(page_type='1', code=X)`，
**返回项 `code === X` 且 `brand_id === 1`（STD）** 才算 STD。

- `code` 是 LIKE 前缀匹配 → `RM758338M` 会同时命中 `RM758338MD6`，**必须精确比对**。
- ⚠️ `page_type` 必须是**字符串 `'1'`**；传数字 `1` 会被上游 pydantic 拒绝：
  `1 validation error for std_product_info_queryArguments / page_type / Input should be a valid string`。
- ⚠️ **STD 货号全集不可枚举**：`std_product_info_query` 不带 code 时能列目录，但 limit 硬顶 500
  （实测 rows=500、distinct=500 即截断；按 `code='RM0'…'RM9'` 前缀查也是各 500，合计 5000 仍不全）。
  → 只能**逐货号精确探测**，不能靠拉目录后做集合匹配（曾因此算出 0.00% 的错误结论）。

**货号判定持久缓存**（`std-goods-verdicts.json`，v1.4.0 新增）：

- 「某个货号是不是 STD」是与统计区间无关的**产品属性**，而结果缓存是按区间失效的 →
  判定结论单独落盘：`STD_VERDICT_FILE`、TTL 90 天（`STD_VERDICT_TTL_MS`）、上限 20000 个货号。
- 写入方式：先写 `.tmp` 再 `renameSync` 原子替换，避免半截文件；
  读取时过期条目丢弃、坏文件当空表（不阻塞主流程）。
- 意义：第二次打开面板时绝大多数货号直接命中缓存、**不消耗探测预算**，STD 卡从分钟级降到秒级。

**探测预算与停止条件**：

| 约束 | 默认值 | 说明 |
|---|---|---|
| `stdSigningMonthsMax` | 4 | 从区间末月往前最多回看几个月（出库明细一个月就要 2 次调用，全区间取不完） |
| `stdSigningShipBudgetMs` | 45000 | 出库明细取数的墙钟预算，到点停手，已取到的部分照样参与计算 |
| `stdProbeBudget` | 150 | 已判定货号**个数**上限（按签单额降序探测） |
| `stdProbeBudgetMs` | 90000 | 探测的总墙钟封顶（**命中缓存的不消耗预算**） |
| 金额覆盖 | 95% | 已判定货号累计签单额 / 窗口签单额达到 95% 即停手 |

⚠️ **探测必须串行**（2026-10-26 实测）：上游 std MCP 在**单 session 内串行处理**请求，
单条 `std_product_info_query` 本身要 6~8 秒。并发 8 个探测时单次耗时被拉长到 **41~55 秒**，
全部超过 `requestTimeoutMs`（30s）被掐掉 → STD 占比直接变 `null`。
→ 逐个 await，单次超时放宽到 `max(requestTimeoutMs, 60s)`。

**页面必须写明的三件事**（`std.note` 已自动生成，前端原样展示）：

1. 口径是**签单金额**而不是报价金额；
2. 回看窗口是哪一段（`windowFrom ~ windowTo`）、覆盖了多少区间签单额（`coverageSigningShare`）；
3. 货号判定进度（`goodsJudged / goodsTotal`）与均摊近似说明。

**降级**：std 服务（8006 端口）不可用时 `shippingRows = 0` → `status = 'unavailable'`、`stdShare = null`，
`note` 明确写「占比未知（null），**不得按 0% 展示**」。**任何情况下都不把「取不到」画成 0%。**

## 3. 回款与售后（方案 02 (4/4)）

| 指标 | 公式 | 源 |
|---|---|---|
| 回款率 | `已回款 ÷ 签约额` | `sales_order_collection_analysis.overview.collection_amount / signing_amount` |
| 未回款 | **`签约 − 已回款` 自算**（上游原值另存） | 见下方「未回款归一」 |
| 账龄 30/31-60/61-90/>90 天 | 按 `overdue_days` 分桶求**归一后**未回款 | `data.orders[]`（含 `overdue_days`、`account_period`） |
| 超 90 天逾期客户明细 | 过滤 `overdue_days > 90`，按金额降序 | 同上 |
| 问题单 | `problem_order_count` / `sale_state` | 同上 |
| 售后闭环率 | `closed ÷ knownState`（**只算状态已知的**） | `mcp__std__after_sale_management_query`（`status2`：1 闭环 / 2 未闭环 / 缺失 = 状态未知） |
| 平均处理时长 | `update_time − add_time` 均值 | 同上 |
| 售后根因 | `back_cause` 分布 | 同上（业务员瞎承诺 / 产品团队不给力 等自由文本归类） |

#### 未回款归一（v1.4.0，审计 A3/A4/A5 修复）

上游 `uncollected_amount` 在**订单级**会把「已部分回款」的订单按**全额**计入未回款，数值虚高；
而它自己给出的 `overview` 级未回款恰好等于 `signing_amount − collection_amount`
（实测 2026 YTD：`11,900,000.00 − 8,200,000.00 = 3,700,000.00`，与参照看板 D5 完全一致）。

因此统一改为**自算归一**：`normalizeUncollectedAmount(signing, collected, upstream)`

- 主看板 KPI / collection 数据卡 / 账龄分桶 / 逾期明细 / 客户档案订单 / 业务员档案订单 / `collection.overview`
  **七处全部走同一个函数**，不再各算一套；
- 归一值下发 `uncollectedAmount`，上游原值一律另存 `uncollectedAmountUpstream`，差额与回落条数写进 `note`；
- 回落策略：`signing`/`collected` 任一取不到 → 退回上游值，并计入 `agingFallbackCount` / `agingUncollectedNote`；
- 回归保护：selfcheck 第 9 节断言 overview 级「签约 − 回款」与上游 `uncollected_amount` 差 < 0.02，
  保证主 KPI 与参照看板 D5 对齐。

> ⚠️ **业务员档案的那个 P0**：`member.dashboard` 曾把 `back_money`（**回款额**）当成未回款额下发，
> 导致页签 9「在途未回款」显示的其实是已回款。现在改走同一归因函数，`back_money` 只作为 `collectionAmount`。

> `sales_order_collection_analysis` 的 limit 被服务端硬钳 500 且**无分页** →
> 逾期明细最多 500 条，超出时在 completeness 里写 `totalKnown=false`，不假装全量。
>
> **账龄与逾期明细是样本，不是全量**（实测 2026 YTD）：
> `overview` 的计数（订单 1,200 / 未付 320 / 逾期 120 / 问题单 17）是**全量**，
> 而 `data.orders[]` 只能拿到 `rowLimit` 条明细（本轮 100 条）。
> 因此 `collection.aging` / `collection.overdue` 必须是对象并自带
> `sampled:true` / `sampleSize` / `totalKnown` / `totalKnownDetail` / `note`，
> 页面必须显示「账龄基于前 N 条订单样本，非全量（全量逾期 313 单）」。
> `collection.problem` 是**全量计数**（来自 overview），标 `sampled:false`。
>
> 售后类型 `type` 是数字枚举码，ERP 未提供码表 → 原样显示并附 `typeNote`；
> 重大投诉根因用正文关键词识别，属**近似口径**，附 `majorBasis` 说明。
>
> **售后闭环三态（v1.4.0，审计 E3 修复）**：原来 `closed = (status2 === 1)`，
> 于是 `status2` 缺失的行一律被判成「未闭环」，未闭环数虚高。
> 现在每行给 `closeState`（`closed` / `open` / `unknown`），块级给
> `open` / `unknownState` / `knownState` + `closeStateNote`，**闭环率分母只用 `knownState`**。
> 前端对应「已闭环 / 未闭环 / 状态未知」三块 + 明细表「是否闭环」列。

- 定义：**近 N 天无订单**（默认 N = 90，可配）且历史有签单的客户。

         ∪ `sales_performance_ranking.department_name`）。

    ④ 最后剔除**已转正**：`positive_time` 有值且 ≤ 基准日 → 已转正；
       `positive_time` 为空（转正日期未回填）→ 算未转正；`positive_time` 晚于基准日（已排期未到期）→ 也算未转正。
  - ⚠️ **「`job_no` 以 `YX` 开头」不能当判据** —— 市场发展部业务员10的 username 也是 `YX90017`（实测）。
    v4 曾用这条规则兜底，结果把 3 个非销售（业务员12·市场发展部、业务员09·市场发展部、业务员11·行政法宣部）漏进新兵表；
    v5 已删除该规则。复验结果（2026-01-01 ~ 2026-10-25 基准日 2026-10-25）：
    新兵表 **10 行全部是未转正的销售序列**
    （部门为蛟龙特训营/猛虎特训营/鲲鹏特战队，岗位全部「业务咨询经理」），
    note 写明「花名册共 224 人 → 剔除非销售序列 134 人、剔除已离职 56 人、剔除已转正 24 人、剔除非销售岗 0 人，实际列示 10 人」。
  - **新兵业绩**：`sales_performance_ranking` 的行**没有 username**，连不上花名册；
    改用 `mcp__erp__member_performance_analysis`（有 `username` / `order_total_amount` / `customer_count` / `order_count`）
    以 `job_no ↔ username` 做主键连接，取不到时退化按姓名匹配。
    签约额口径：优先 `ranking.signing_amount`，取不到退到 `member.order_total_amount`，都取不到填 0 且 `signingSource = 'none'`。
  - 「转正进度」= 区间业绩 ÷ 转正门槛（金额进度），**不等于公司转正评审结论**；
    产品/技能考核明细、师傅评价、预计转正日期 ERP 无字段 → 表中不展示，并写进表下说明。

## 8. 缓存与降级

- 缓存 key：`erp-sales-dashboard|<startDate>|<endDate>|<squad>|<member>`；TTL = `cacheTtlMs`（默认 6 小时）。
- `refresh=true` 跳过缓存。
- **入缓存的判定是「有没有取数失败」**：`calls[]` 里 `ok === false` 的条数为 0 → 写内存缓存 + 落盘；
  有失败 → 不写缓存，并给中文说明「本次有 N 个数据源取数失败，结果不完整，未写入缓存；下次打开将重新取数」。
- **告警（warnings）不阻止缓存**。告警是「某个口径按预算取数」的**信息类提示**（例如「STD 判定探测达到预算上限 24 个货号」，
  其余货号按未知处理），它描述的是**口径边界**而不是**取数失败**。早期版本用「零告警才缓存」，
  而本插件恒有 1 条 STD 预算告警 → 缓存永远不命中 → 用户每次打开面板都要重拉 3~5 分钟（这是真实用户反馈过的现象）。
  现改为：告警随结果一起缓存、一起显示（页面顶部 warnings 折叠区），口径边界依然对用户可见。
- 缓存命中时 `meta.cached = true`、`meta.cacheUntil = 命中时刻 + TTL`；新算的结果 `meta.cacheUntil = now + TTL`，
  页面据此显示「剩余 X 小时 Y 分」，用户能一眼看出什么时候会过期。
- 任何板块的 MCP 调用失败 → 该板块返回 `null` + `warnings[]` + `calls[]` 里 `ok:false` 与原因摘要（压到 160 字，避免上游 SQL 错误破版）。
- **实测（v5）**：`verify-host.mjs --cache-test` 同参数连发两次 → 首次 52.3 秒，第二次 **1 毫秒**（命中磁盘缓存），
  `meta.cached = true`、`meta.cacheUntil` 正确。

## 8·五、AI 分析侧栏（对话口径）

AI 对话**不产生新的数据口径**，它只是对**已经取到的、已经算好的**当前页签数据做解读和追问。

- **上下文边界**：`buildAiContext(tabId, data)` 只喂**当前页签**的那一块 + `period`（区间）+ `filters`（当前筛选条件），
  截断到 12000 字符。所以 AI **只能回答当前页签能回答的问题**；越界时它必须回「当前只加载了本板块数据，无法回答」。
- **历史折叠**：历史问/答成对折成一条 `问：…\n答：…` 的 **user 消息**，全程只发 user 角色。
  原因：DSH llm 服务收到**带正文的 assistant 消息**会抛
  `Cannot read properties of undefined (reading 'replayState')` → 全部候选模型失败 → `ai.chat` 返回 500。
  对照实验：assistant `content` 为空串 / 无 `content` 字段 / 连续两条 user 消息，都正常。
- **数字纪律**：系统角色里写死「所有数字必须来自 JSON，缺失口径就说不可得」，禁止模型自己算同比/环比。
  实测：问「本月接单额多少？同比如何？」→ 模型回「本月接单额 1,814,702.06 元；本月同比**不可得**，缺少 2025 年 10 月同口径数据」，
  口径缺失时**没有编数字**。
- **模型选择**：候选优先级 `config.aiProvider/aiModel` → `ctx.get('agentDefaultModel').currentSelection()`
  → 注册表里 minimax 首个模型 → 其它 provider 首个模型；每个候选先 `effort='low'` 再 `null`，最多 5 个。
  **候选对象只有 provider/model 两个字段，API key 不进候选、不进日志、不落盘。**
- **限制**：AI 看到的 ABC 结构 / 客户分档 / 复购 / 沉睡 / 跟进都是**抽样口径**，
  回答里应带样本量；不能替代口径说明，也不能回答 ERP 根本没有的指标（9 渠道归因、订单级 ABC、培训明细）。

## 8·六、跨设备连接器前缀（换设备不掉数据）

同一个插件要能在**别的机器**上跑起来，最大的坑不是代码，是 **DSH 的 MCP 连接器名字**：
工具全名 = `mcp__<连接器名>__<工具名>`，`<连接器名>` 是用户在 DSH 里给自己那个连接器起的名字，
**每台设备都可以不一样**。写死 `mcp__erp__` 的插件，换台机器名字叫 `erp-cn` 就整片「工具不可见」。

**发现机制**（Host 半，`resolveToolPrefixes` + `readMcpConnectors`）：

1. 候选根目录：`process.env.DSH_HOME` → 由 `process.env.DSH_PROFILE_DIR` 上溯两级 → `os.homedir()/.dsh`。
2. 读 `<root>/storages/mcp_connector.json`，取 `tables.connections[*]` 的 `serverName` / `url` / `enabled`。
   ⚠️ **只读这三个字段**；`auth.apiKeyValue` 等凭据字段一律不读、不解析、不落盘、不进日志。
3. 认领：先按 **url 端口**（8001=erp / 8006=std / 8003=planning），再按 **serverName 同名**。
4. 前缀优先级：`config.toolPrefixes`（用户配置）> 注册表按端口 > 注册表按名 > 内置默认。
5. 兜底：首选前缀「工具不可见」（UNKNOWN_TOOL / unknown tool / not found / 不可见 / 不存在）时，
   依次试「配置 → 发现 → 默认 → 其它已启用连接器」去重后最多 4 个候选；
   **真实错误（抛错，或 isError 但不是「不可见」类）立即停止**，不用试错掩盖真实故障。
6. 可视化：`meta.toolPrefixes`（本次实际用的前缀）与 `meta.toolPrefixSource`（`config` / `discovered` / `default`）
   随响应下发，页签 10「MCP 连接器（本机）」展示；认领不到时给 amber 提示与 `cordis.patch.yml` 配置指引。

**自证**：selfcheck 第 14 节 6 项行为级断言守住（默认回退、按端口认领、改名后兜底、配置优先、非法配置忽略、端口解析），
端到端 `verify-host.mjs` 在本机实测三个分组全部 `discovered`、零告警、业务指标与写死前缀时完全一致。
